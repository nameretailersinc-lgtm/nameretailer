### Filters, pagination and canonical rules

Curated clean routes are self-canonical `index,follow` when ready. Metric/range controls survive consolidation as filters. Query keys use an allowlist (`daMin`, `daMax`, `drMin`, `drMax`, `tfMin`, `tfMax`, `trafficMin`, `trafficMax`, `backlinksMin`, `backlinksMax`, `priceMin`, `priceMax`, `niche`, `country`, `language`, `sort`, `page`); values are validated, defaults removed, order normalized, range endpoints defined consistently. Camelcase query keys are intentional API names; public path slugs remain lowercase. Specify half-open bands except the closed lowest/upper bounds so adjacent ranges do not double-count boundary values.

Arbitrary combinations and user sorting use `noindex,follow` and normalized self-canonical including content-changing filters. Do not also canonicalize materially different filtered content to the unfiltered homepage. Tracking-only parameters use the clean equivalent canonical. Empty legitimate filter states return 200 with noindex and clear recovery; invalid or impossible pagination returns 404. Avoid link-generated Cartesian filter combinations; use forms for exploratory filters. Do not rely on noindexed filter pages as the only discovery path because sustained noindex may reduce link crawling.

Pagination of indexable clean archives uses `?page=2`, etc., with unique title, self-canonical and crawlable previous/next numbered `<a href>` links; page 1 omits the default parameter. Later pages show their actual items; no canonical-to-page 1. Pagination inherits noindex for arbitrary filtered/sorted states. Infinite scroll or Load More enhances, rather than replaces, server-visible paginated links. Google does not use `rel=prev/next`; these are not a dependency. [Google pagination guidance](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading).

SSR/ISR renders primary public text, relevant links and initial listings. Account state/cart counts hydrate without making public output personalized. A cached public page must never contain another customer's identity/cart. One H1 per page; accessible answer blocks, semantic table headings and mobile comparison alternatives follow UX planning. Each indexable route receives a relevant contextual inbound link, not only mega-menu presence; an orphan CI check covers all publishable routes, with deliberate footer/body links to legal and policy pages.

## 2. Redirect map and activation contract

[redirect-map.csv](redirect-map.csv) has `old_url,new_url,status,reason,source`: exactly 166 audit URLs, each once. `keep` retains the same URL; `301` proposes a direct permanent redirect; `410` has a blank destination and proposes intentional retirement. [redirect-system-rules.csv](redirect-system-rules.csv) separates patterns, unknown mappings, feeds, WordPress APIs/IDs/media, archive pagination and commerce compatibility. Pattern rules are not executable CSV rows.

**The map is a review proposal, not an activation file. Never feed it blindly into a redirect generator.** Fixed code generation in Phase 4 accepts only an explicit approved activation manifest. That manifest records source, final target/status, reviewer, evidence reference, destination verification and activation date. All semantic 301/410 proposals require review of available crawl/content and performance/backlink evidence, a source backup, replacement relevance, imported unique content and target readiness. Request GSC/backlink exports and record the data gap if absent; their absence does not automatically block an evidenced crawl-based merge authorized in the approved activation manifest. Materially uncertain meaning, buyer requirements or replacement relevance keeps the affected source preserved pending resolution. Approval of Phase 1 alone does not activate the map. Protocol/www/slash normalization is separate and still needs final-status/one-hop verification.

The six monthly routes stay `keep` until billing/duration meaning is confirmed. Five detail probes stay `keep` pending utility requirements; this is route compatibility, not approval to index them. If private buyer details are needed, require auth, ownership rules and noindex; if intentionally retired, change verified URLs to 410 after review. `/hello-world/`, `/test-blog-post/`, `/community-guidelines/`, `/user-reviews/` have conditional 410 proposals; lack of supplied community/review evidence is not proof nothing existed.

Consolidations include DA/DR/TF/traffic/backlink bands into curated hubs; existing TF slug remains despite its narrow wording. The survivor must explain all supported ranges clearly, with the old range preselected where a verified filter contract supports it. Any destination-query revision must be reflected in the activation manifest and tested. Price bands remain provisional. `/products/` to `/` is the proposed relevant marketplace archive replacement; `/product/link-purchase/` is a separate commerce compatibility problem and must not be caught by that decision. Peripheral community/blog redirects only activate if a genuinely equivalent archive/replacement retains useful material; otherwise revise to preservation or confirmed retirement instead of an unrelated catch-all.

### Implementation handoff (Phase 4)

Fixed approved 301s are generated into `next.config` using explicit `statusCode: 301`, omitting `permanent`. Next.js `permanent: true` emits 308, not 301. Validate against the stable version selected at scaffold; if framework normalization causes extra hops, handle exact public GET/HEAD redirects at Caddy/proxy before normalization. Keep `trailingSlash: true`, but do not assume its automatic 308 meets the brief's exact 301 requirement. 410 requires a route/proxy HTTP 410 response; `next.config` redirects cannot implement retirement. [Next.js redirect behavior](https://nextjs.org/docs/app/api-reference/config/next-config-js/redirects).

DB redirects use a cached lookup invalidated on admin save, with no hot-path DB hit. Normalization resolves the approved final destination first so `http://www.../old` reaches the canonical survivor in one hop. Reject loops/chains, duplicate/conflicting sources, unsafe external targets, protected commerce/API sources and targets returning non-200/noindex when intended for SEO transfer. Do not lowercase signed queries or forward secrets/tokens into redirect Locations. Mutating/API/payment requests keep their method and semantic handler; migration SEO rules match public GET/HEAD only. Unverified `?p=ID` or old media filenames must not be guessed. Back up source content/media and retain verified redirects for at least a year, preferably indefinitely when useful. Unknown routes 404, not homepage 301.

SEO editors get unique-title/description warnings, canonical preview, readable length counters (guidance, not fixed Google limits), missing-alt/orphan checks, FAQ blocks feeding the same visible answers and JSON-LD, and source/date reminders. Focus-keyword score is editorial guidance, not a ranking score. Canonical defaults to absolute self-reference; overrides are validated for legitimate equivalents, not used to hide distinct pages or private data. Publishing invalidates page, related routes, sitemap and llms caches; `lastmod` reflects substantive updates, not every build or stock tick. Only published indexable 200 canonical routes enter sitemap; large sets split with an index. Draft/scheduled/empty placeholder/private/error/redirect URLs are excluded.

Robots/settings edits require Admin role, audit history, preview/lint and recovery export. Provider credentials are secrets with redacted UI and server-only access; verification/analytics IDs are not equivalent to API keys. The admin SEO UI cannot override mandatory private-route authorization or noindex protections.

## 4. Structured-data plan

Use typed `schema-dts` builders in `lib/seo/` and one escaping-safe server JSON-LD component in Phase 4. Stable absolute `@id` references reuse Organization/WebSite/author identities. Markup must describe actual visible page content; arbitrary HTML/script injection is rejected. No Review/AggregateRating without real visible verifiable reviews; do not convert an inventory claim into a rating.

|---|---|

| Homepage | `WebSite` with brand and canonical URL; `SearchAction` optional only after actual public on-site search exists, using its real query URL |

This supersedes the earlier health/government-only guidance in the agent prompt. [Google 2026 documentation changelog](https://developers.google.com/search/updates#may-2026). HowTo rich results were deprecated in September 2023. [Google announcement](https://developers.google.com/search/blog/2023/08/howto-faq-changes). ## AEO content and GEO evidence

Answer-first editor blocks use question H2/H3 plus roughly 40–60 words answering directly, then nuance/evidence, not a rigid word target. Long guides add a short summary, optional definition, meaningful comparison table, steps and accessible FAQs. Editors review accuracy and policy-sensitive paid-link advice; no fabricated PAA attribution, metrics, authors or guarantees. Speakable is optional/experimental and outside baseline launch; no promised voice-search benefit. Paid placements must be described accurately and links qualified where required by [Google paid-link guidance](https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links).

No AI engine publishes a complete, guaranteed citation/ranking formula. Engines do publish access and content guidance; this does not establish a ranking-factor list. Categorize the following tactics explicitly:

| Tactic | Evidence level and purpose |
|---|---|
| Useful original content, clear headings, accessible HTML, crawlable internal links, truthful citations and update dates | Evidence-backed best practice: improves discoverability and comprehension; does not guarantee AI citations |
| Confirmed Organization identity, real author evidence, editorial policy/contact transparency, consistently displayed address/email | Low-risk best practice: supports trust/entity clarity; no claim these are separate AI ranking factors |
| First-party full-inventory research with methodology/provider/date and owner permission | Low-risk best practice if accurate/original; biased crawl sample cannot stand in for complete inventory |
| `/llms.txt` and `/llms-full.txt` | Experimental emerging convention, not confirmed ranking signals; offer concise public route descriptions/full reviewed public text only; Google says these files do not improve or harm Search visibility/rankings |
| AI referrals/citations observation | Best practice measurement: capture consent-appropriate referrals and manually sample citations; incomplete attribution and personalization prevent a clean ranking score |

Google says normal SEO remains relevant and no special AI markup is required. [Google AI-feature guidance](https://developers.google.com/search/docs/appearance/ai-features). Its June 15, 2026 clarification says llms files have no Search ranking impact. [Google documentation update](https://developers.google.com/search/updates#june-2026). These experimental files are generated from approved public DB content and editable settings; exclude customer details, emails submitted in forms, unpublished work, secrets and noindexed previews. They are publishing conveniences, not security controls or permission bypasses.

### Crawler policy and private-route visibility

Owner default allows reputable AI crawlers on public content. Treat search discovery, user fetches and training separately; allowing training does not guarantee citation in live answers. OpenAI distinguishes OAI-SearchBot (search), GPTBot (potential training) and ChatGPT-User (user-initiated requests; robots rules may not apply). [Official bot documentation](https://developers.openai.com/api/docs/bots). Anthropic distinguishes Claude-SearchBot, Claude-User and ClaudeBot (potential training). [Official crawler policy](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler). PerplexityBot serves search discovery, while Perplexity-User makes user requests; check their documented behavior before rollout. [Perplexity policy](https://docs.perplexity.ai/docs/resources/perplexity-crawlers). Google-Extended is a usage-control token, not the Google Search crawler or a Google Search ranking opt-in. [Google common-crawler documentation](https://developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers#google-extended).

Also retain the requested Applebot-Extended and CCBot policy slots, with current purpose/robots details checked at implementation rather than implying they are answer-engine search crawlers. Specific allow groups must repeat private-path restrictions: they do not automatically inherit wildcard groups. Sitemap references canonical public URLs. WAF access checks verify genuine bot identity using current provider verification guidance rather than trusting only User-Agent text.

Robots disallow is crawl control, **not authentication**. Disallowing a route can prevent crawlers reading its noindex, leaving a discovered URL in results without content. Private cart/checkout/account/admin APIs require server auth/ownership+noindex+private no-store regardless of crawler behavior. The baseline commerce disallow requested in the brief is retained as crawl reduction with this documented tradeoff; if an already indexed public login/commerce URL needs removal, permit only its safe anonymous shell to be fetched with noindex during cleanup or use Search Console removal, without exposing private content. Arbitrary filter/search pages relying on noindex remain crawlable; block excessive facets only after indexed-state review and accepting reduced noindex visibility. [Google robots/noindex guidance](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

## Phase 3 CMS support: implementation and limits

Implemented on 2026-10-05 without enabling the public migration layer:

- `lib/cms/validation.ts` validates each CMS collection, user creation and non-secret settings. Server-managed fields and unknown content fields are stripped. Published/scheduled posts require an actual verified active author record; archiving or unverifying that author is rejected while published/scheduled posts reference it. The 30-readable-word publication floor is a minimum editorial safeguard, **not** proof of originality, usefulness or SEO readiness. Dates are accepted as ISO timestamps and persisted in UTC so indexed scheduling comparisons are chronological. Future publication/review/consent dates are rejected where they would misrepresent completed events.
- `lib/cms/content.ts` sanitizes stored rich text, preserves readable block boundaries and strips scripts, SVG, styling, unsafe links/images and arbitrary embeds. Only named HTTPS YouTube privacy/Vimeo player embeds survive; published body images require an explicit alt attribute, with empty alt permitted for an intentional decorative choice. Uploaded media similarly needs meaningful alt or an explicit decorative flag. Paid-link qualifications (`sponsored`, `nofollow`) and user-content qualification (`ugc`) survive sanitization. New-window links gain `noopener noreferrer`.
- The same module supplies editorial checks, relevant published-content link suggestions and dashboard warnings for missing metadata, duplicate titles, missing alt and possible orphans. The focus-phrase score is editorial guidance, not a ranking score. A possible-orphan warning only checks published CMS relationships/body links; it cannot account for future template links or certify the complete public link graph.
- `lib/cms/redirects.ts` parses an explicitly separate `source,target,statusCode` CSV, validates every row before persistence, and derives stable default slugs from normalized sources rather than batch positions. Imports and record writes remain **disabled configuration** in Phase 3. Duplicate sources, self redirects, chains, loops, unsafe/external destinations and private/payment/API/media/design/discovery paths are rejected. The planning migration CSV is deliberately not accepted as an activation import. Replacement relevance, actual target HTTP/indexability checks and the approved activation manifest remain Phase 4 responsibilities.
- `lib/seo/metadata.ts` prepares metadata and sitemap-entry builders. Published robots choices are honored; drafts/scheduled/archived content defaults to noindex/nofollow. Canonicals are same-origin public equivalents, normalized to lowercase trailing-slash paths and disallow query/fragment/private/discovery targets. Sitemap candidates exclude unpublished, noindexed and alternate-canonical records and use the actual stored update timestamp, never a build date. **No public route calls these builders yet**; response-status, route-readiness, pagination/filter and substantive-lastmod checks belong to Phase 4.
- `lib/seo/structured-data.ts` prepares typed Organization, Article/BlogPosting and FAQ builders with raw-script-safe JSON serialization. Article authors must match the referenced verified active record. Empty sanitized FAQs are omitted/rejected. Unconfirmed profiles, phone/legal identity, ratings and reviews are not invented. Templates must still show the same facts and visible answers before rendering these builders in Phase 4; general FAQ schema is not a promise of Google rich results.
- `lib/cms/exports.ts` exports versioned JSON, spreadsheet-safe JSON-backed CSV and content-portability WXR. WXR splits CDATA terminators, escapes XML text, removes XML-forbidden raw controls and stores each original record as JSON post metadata; scheduled content uses its actual scheduled timestamp. CSV prefixes formula-leading plain fields with an apostrophe: this is intentional spreadsheet safety, not byte-identical title round-trip. These exports are **not** full MongoDB/media/user backups, a complete WordPress compatibility migration, or tested restore/import workflows. Filenames are fixed rather than derived from untrusted titles.

Verification: **69 focused Vitest tests passed** in `tests/unit/cms-content.test.ts`, `cms-validation.test.ts`, `cms-redirects.test.ts`, `cms-seo.test.ts` and `cms-exports.test.ts`. They exercise malicious/nested encoded URLs, XSS and embeds, alt decisions, UTC scheduling, real author guards, FAQ sanitization, metadata privacy, sitemap candidate exclusions, JSON-LD serialization and JSON/CSV/WXR portability. ESLint passed for the owned helper/test files and the project TypeScript check passed at this checkpoint. Runtime API/database/browser evidence is reported separately by the orchestrator; pure helper tests do not prove deployed public SEO or CMS end-to-end behavior.

No conflict with the approved design or UX plan. Owner input remains necessary for real author identities/credentials, original publishable content, actual social profiles, migration/source exports, listing data and uncertain product meaning. Analytics IDs can be stored, but no analytics/pixel script is activated before the later consent-aware public implementation. Robots/llms editors store configuration only; linting/merging mandatory private rules, complete structured-data templates, live redirects, sitemap/status checks and public crawl controls remain the next public phase.
